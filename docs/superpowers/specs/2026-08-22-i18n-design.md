# Design: Full app localization (EN base, PL translation)

Date: 2026-08-22
Status: approved

## Goal

Localize the entire zte-menu app into English and Polish. English becomes the
base/source language of the project; Polish becomes a translation. The app picks
the system language by default, with a manual override in Settings.

## Scope

In scope:

- Runtime string localization for all user-facing text (popover, settings
  window, menu bar, Info.plist permission prompt).
- Language override picker in Settings: System / Polski / English.
- Source-code language switch to English: comments, script `echo` output,
  test names and fixtures, README.
- Model types stop returning display strings; they return enums.

Out of scope:

- Historical documents under `docs/superpowers/` dated 2026-07-15. They record
  decisions already made and stay in Polish.
- A Polish README. `README.md` is English-only.

## Architecture

### Localization module

Three new files under `Sources/ZteMenu/Localization/`:

| File | Responsibility |
| --- | --- |
| `AppLanguage.swift` | `enum AppLanguage: String, Codable, CaseIterable { case system, pl, en }` and resolution of `.system` to a concrete code via `Locale.preferredLanguages` (a `pl` prefix maps to `pl`; anything else maps to `en`). |
| `LocKey.swift` | `enum LocKey: String` listing every key. Keys are a type, so a typo is a compile error rather than a missing translation at runtime. |
| `L10n.swift` | `@MainActor @Observable final class L10n`. Holds the resolved `Bundle` for the active language and exposes `callAsFunction(_ key: LocKey, _ args: CVarArg...) -> String`. |

`L10n` is constructed in `AppDelegate` alongside `settings` and `updater`, then
passed explicitly into `PopoverView` and `SettingsView`. No singleton, so tests
can build an instance with an arbitrary language.

### Bundle resolution and fallback

`L10n.setLanguage(_:)` resolves the active code and loads
`Bundle(path: Bundle.main.path(forResource: code, ofType: "lproj"))`.

Lookup order, so that `swift run` and `swift test` work without an assembled
`.app`:

1. The resolved `.lproj` bundle inside `Bundle.main`.
2. The same `.lproj` inside `Bundle.module` (SwiftPM target resources).
3. The English table, as the base language.
4. The raw key, so a missing string is visible rather than silent.

### Reactivity

`SettingsStore.settings.language` gains an `AppLanguage` field defaulting to
`.system`. Changing it calls `L10n.setLanguage(_:)`; because `L10n` is
`@Observable`, SwiftUI re-renders the popover and the settings window
immediately. No relaunch.

## Model changes: enums instead of display strings

Three places currently return Polish text from logic code. They move to types,
which keeps presentation in the view layer and makes the tests
language-independent.

| Before | After |
| --- | --- |
| `ModemData.signalDescription -> String` | `ModemData.signalQuality -> SignalQuality` (`none`, `veryWeak`, `weak`, `medium`, `good`, `veryGood`) |
| `AppState.error(String)` | `AppState.error(ModemErrorKind)` (`loginFailed`, `unreachable`) |

`ModemData.networkLabel` is unchanged. `5G` and `WCDMA` are technical names and
are not translated; only the empty case renders as an em dash.

Affected existing assertions:

- `ModemDataTests` — compares against `.veryGood` and `.none`.
- `ModemStoreTests` — compares against `.error(.loginFailed)`.

## Resources and build pipeline

The `.app` bundle is assembled by hand in `scripts/build-app.sh`, with no Xcode
project, so resources must be copied explicitly.

```
Resources/
  en.lproj/Localizable.strings   # base language
  en.lproj/InfoPlist.strings
  pl.lproj/Localizable.strings
  pl.lproj/InfoPlist.strings
```

- `Package.swift`: the `ZteMenu` target declares both `.lproj` directories via
  `.copy`, so they are reachable through `Bundle.module` during development and
  in tests.
- `scripts/build-app.sh`: copies `Resources/*.lproj` into
  `$APP/Contents/Resources/`.
- `Resources/Info.plist`: `CFBundleDevelopmentRegion` is set to `en`,
  `CFBundleLocalizations` to `en` and `pl`. The English text for
  `NSLocationWhenInUseUsageDescription` lives in `Info.plist` as the base value;
  `InfoPlist.strings` overrides it per language.
- `SettingsView.lastCheckLabel`: `RelativeDateTimeFormatter` no longer hardcodes
  `pl_PL`; it takes its `Locale` from `L10n`.

## Source language switch

English becomes the source language across the repository:

- Comments in `Sources/` and `Tests/`.
- `echo` output and comments in `scripts/*.sh` and `.github/workflows/release.yml`.
- `README.md`, rewritten in English with no Polish counterpart.

The existing Polish user-facing strings are preserved as the content of
`pl.lproj/Localizable.strings`. They stop being the source of truth and become a
translation.

## Testing

New `Tests/ZteMenuTests/L10nTests.swift`:

- `.system` resolution across representative `preferredLanguages` inputs,
  including a Polish locale, a non-Polish locale, and an empty list.
- Key completeness: every `LocKey` case has an entry in both `en` and `pl`.
  This is the test that catches a forgotten or misspelled translation.
- Fallback behaviour when a bundle is absent and when a key is missing from a
  non-base language.

Updated existing tests: the three assertions listed under "Model changes".

Verification: `swift build && swift test` (44 existing tests plus the new ones),
then `./scripts/build-app.sh` and a manual run exercising the language picker in
both directions.

## Risks

- Hand-assembled bundle: if the `.lproj` copy step is missed, the app silently
  falls back to raw keys. The fallback chain makes this visible rather than
  crashing, and the completeness test guards the translation tables themselves.
- Broad source-language rewrite touches many files without changing behaviour.
  The test suite is the regression guard; no logic changes ride along with the
  comment translation.
